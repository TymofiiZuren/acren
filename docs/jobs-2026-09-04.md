# Client jobs — 4 September 2026

## Delivered scope

Continued the planned client-work slice without introducing rates, invoices, firm sharing or external sending. Each client profile now lists jobs, supports adding a title/optional planning date and offers the allowed next statuses. Planned work must start before completion. Completed work can reopen; cancelled work can replan. Titles/dates are fixed after creation in this first slice, and the form explicitly explains cancellation/replacement and unsaved-draft limits.

Existing panel, field and button styles were reused. UI/UX guidance informed visible labels, inline errors plus a focused summary, pending controls, explicit save feedback, narrow-screen stacking and truthful history limits. No new dependencies or hydration-warning suppression were introduced.

## Database boundary and rollout

Applied additive migration `20260904150000_client_jobs.sql` to local Supabase with `npx --yes supabase@2.116.0 migration up --local`. Apply it before this UI on other environments. Existing client CRUD is compatible and no client records were deleted or modified by the migration. No hosted environment was changed.

- Jobs and job events enable and force RLS, scoped by caller identity.
- Composite `(client_id, consultant_id)` foreign keys prevent mismatched ownership even independently of the app's filters.
- Ordinary roles can insert job input fields and update status only. They cannot change IDs, ownership, linkage, dates/titles after creation, versions or timestamps, or delete jobs/history.
- An invoker trigger verifies an accessible active client, using a row SHARE lock to serialize against archive updates. The database validates allowed transitions and increments the version only on real changes.
- A fixed-search-path definer trigger records creation and status changes transactionally. Its direct execution is revoked. Events omit title/contact copies. No-op saves create no event.
- Server Actions verify the session, validate input, keep provider errors private, and use the caller's session. Updates require the version the user saw. A stale save affects zero rows, refreshes server data and returns a warning.
- New-job forms carry a unique request ID. Database uniqueness prevents replay duplicates. On a duplicate, the action accepts only an exact payload match visible to that caller. A freshly opened form is a distinct request and can deliberately create another similarly titled job.
- Privileged database administrators retain access. Approved client erasure cascades to jobs and events. This is not an administrator-proof audit ledger; retention, rights requests and backup expiry remain operator responsibilities.
